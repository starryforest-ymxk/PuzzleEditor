## 1. 总体判断

项目的目录和领域划分清楚，具有持续维护的基础；当前跨模块规则、前端类型保障及自动化检查不足，尚不能评价为规范执行充分、维护成本低的成熟编辑器。

## 2. 需要优先处理的正确性问题

### P1：演出图级操作遗漏撤销、未保存状态与只读保护

证据：`store/reducer.ts` 第 23–56 行与 `store/slices/presentationSlice.ts` 第 13–28 行。黑板中的创建入口位于 `components/Blackboard/BlackboardPanel.tsx` 第 529–539 行。

`ADD_PRESENTATION_GRAPH`、`UPDATE_PRESENTATION_GRAPH`、`DELETE_PRESENTATION_GRAPH` 在领域切片中可修改项目，但没有进入顶层 `HISTORY_ACTIONS`；只读拦截名单又复制自这份名单。

独立场景确认：从已保存状态新建、重命名、删除演出图，`isDirty` 均保持 `false`，撤销历史长度保持 0；新建后执行 Undo，图仍存在。在 Reducer 只读状态下派发新建演出图，项目同样被修改。只读问题是状态层验证，未模拟 UI 是否展示对应按钮。

影响：用户无法撤销这些操作，自动保存和切换前确认也无法依靠未保存标记正确触发。维护问题的根源是 Action 联合类型、Slice 分类名单、历史名单及只读名单分别维护。

建议：建立集中、可检查完整性的业务 Action 分类，明确每类操作是否修改项目、进入历史、允许只读执行；用行为测试覆盖新增领域操作。历史与脏状态的分类应允许明确差异，不能始终使用同一份名单推导全部规则。

### P1：保存后的 Undo / Redo 没有更新未保存标记

证据：`store/reducer.ts` 第 214–250 行。

独立场景确认：“修改项目名称 → 标记保存成功 → Undo”后，项目名称已不同于保存版本，`isDirty` 仍为 `false`；保存撤销结果再 Redo，也出现相同问题。

影响：Header 提示、自动保存和切换前确认均依赖 `isDirty`，编辑内容可能因此没有得到正确保存保护。

建议：统一普通编辑、撤销和重做的脏状态计算；至少保证内容变化时标记未保存，进一步可通过保存版本或内容标识判定是否回到已保存状态。

### P1：保存确认与项目打开入口的保护不一致

证据：`components/Layout/Header.tsx` 第 104–106、142–153、237–245 行；`components/Layout/ProjectMenu.tsx` 的项目打开、浏览器文件读取及最近项目回调。

“保存并继续”调用 `saveProject()` 后没有等待其 Promise，也没有检查成功结果，而是在 100ms 后继续新建或加载。提取实际源码中的 `onConfirmSave` 回调，并用延迟保存替身执行，确认保存尚未完成就已进入新建对话框；随后保存返回失败也不会阻止已经执行的下一步。

此外，Project 菜单通过 `handleElectronLoadProject` 直接调用 `loadProjectFromString`，该路径没有复用 `handleLoad` 中的 `isDirty` 检查。该问题依据实际调用链静态确认，未在真实用户项目上执行切换。

建议：将请求新建、打开、最近项目打开和保存后继续集中到同一项目会话流程，明确取消、保存失败、保存成功三种结果。UI 负责展示对话框，流程负责确保保存成功之后才允许替换当前项目。

## 3. 架构和规范方面的缺口

### 前端类型保障不足

- 根 `tsconfig.json` 没有启用 `strict`；Electron 配置已启用。
- `package.json` 未声明 `@types/react` / `@types/react-dom`，当前 `node_modules` 中也没有相应类型文件。用 TypeScript 编译器 API 检查当前程序，`useEditorState` 和 `useEditorDispatch` 均被推断为 `() => any`。
- 显式的 `any` 还出现在变量值、通用画布节点、Inspector 更新对象及 Action 强制转换中，例如 `types/common.ts:105`、`hooks/useGraphInteraction.ts:33`、`hooks/useInspectorNameFields.ts:20`。
- 临时追加 `--strict` 检查得到 3540 条诊断，其中 2570 条为 JSX 缺少类型接口的 TS7026；React 类型缺失带来大量连锁诊断。这不是 3540 个独立业务缺陷，需先补齐类型依赖再重新评估剩余问题。

建议先恢复 React 类型声明，再逐步收紧前端检查和高风险 `any`。导入边界应使用 `unknown` 与实际校验；变量值可使用基础值联合类型，图交互可依赖已有图节点接口。

React 官方对 TypeScript 支持及相关类型包的说明：[Using TypeScript](https://react.dev/learn/typescript)。严格检查含义参考 [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html)。

### 工具层和项目操作边界与文档不一致

`utils/variableScope.ts` 依赖完整 `EditorState`，若干校验工具依赖 `store/types`；部分 Inspector 为调用作用域函数构造不完整 EditorState 后使用 `as any`。这些类型依赖不等同于已证明的运行时循环依赖，但降低了工具函数独立复用的能力。

`api` 当前主要是抽象接口和类型导出，实际文件调用分布在业务 Hook、Layout 组件及 `src/electron` 包装层。不能将旧文档的 Store → API 图示直接当作现有运行路径，也不宜要求所有业务 Hook 都遵守旧的“禁止依赖 Store”规则。

建议明确纯领域计算、业务 Hook、平台 I/O 和 UI 的职责；作用域、引用和校验函数只接收所需的业务数据与上下文，项目会话流程统一管理副作用和操作顺序。

### 导入归一化缺少明确的数据校验边界

证据：`utils/projectNormalizer.ts` 第 33–65、179–200 行及 `hooks/useProjectActions.ts` 第 395 行后的加载流程。

归一化使用 `any`、类型断言与缺省填充，但这些行为不能验证外部 JSON。独立场景传入 `fileType: 'unrelated-format'` 的无关对象，函数仍生成名称为 `Untitled Project`、根 ID 为空的项目。

建议定义格式识别、最低结构校验、版本兼容迁移和业务校验的顺序；合理的兼容补值应保留，但不能把任意 JSON 的解析成功视为项目加载成功。

### 大型组件的职责和固定样式仍较分散

按源文件物理行数统计，`BlackboardPanel.tsx` 为 978 行，`PresentationCanvas.tsx` 为 974 行，条件编辑器为 633 行。黑板组件同时承担筛选、引用统计、创建、导航、多类拖拽排序和四个页签渲染；演出画布仍组织较多节点/边交互与视觉细节。维护成本来自这些职责组合，不能仅按行数判断。

项目已进行有价值的公共逻辑提取，但还可以按业务职责拆分页签、拖拽配置、引用统计和画布视图组织。扫描发现 67 个组件文件使用 `style={{...}}`，固定颜色和弹窗布局与项目的集中样式要求存在差距；整理规范时应明确固定主题样式和画布动态坐标的处理方式。

### 缺少规范的自动检查和关键流程回归

`package.json` 没有 lint、格式检查、typecheck 或 test 脚本；本次未发现 ESLint、Prettier、Vitest/Jest 配置、测试用例或执行相关检查的 CI 工作流。`build` 仅调用 Vite，不能替代项目类型和行为检查。

本次扫描 `components/store/hooks/utils/api/types/src/electron` 下 179 个 TypeScript 源文件，178 个可严格按 UTF-8 解码；`utils/stageDrag.ts` 无法按 UTF-8 解码，其中文注释字节按 GBK 可正确解释，违反项目指定的编码规则。后续编码修复需要保留注释内容，不能按 UTF-8 误解码后覆盖原文件。

建议先补充状态操作、撤销/保存、保存失败和导入边界的行为回归，再添加类型、格式、依赖边界和编码检查。文档中的规范需要有对应的执行入口。

### 大工程性能需要测量后决定优化范围

当前 `StateContext` 提供整个 EditorState。状态值变化会通知订阅该 Context 的消费者；将 dispatch 拆分出去并不意味着状态订阅已按字段拆分。机制参考 [React useContext](https://react.dev/reference/react/useContext)。

黑板第 184–234 行为每个资源单独查询引用，且多个缓存依赖整个 `project`。据此可以判断存在重复遍历和较宽的更新范围，但本次没有运行大工程基准，不能认定具体帧率或卡顿程度。建议先测量，再选择按领域订阅和共享引用索引等改进。

## 5. 建议改进顺序

1. 修正统一状态约束和项目切换流程，补充失败路径回归，优先保证修改可撤销、可保存、可被正确提示。
2. 恢复 React 类型保障，逐步收紧关键接口；加入可重复执行的类型、规范、编码及业务测试检查。
3. 明确真实的模块边界，按职责拆分大型组件并同步开发文档；通过实际测量决定状态订阅和引用统计优化范围。

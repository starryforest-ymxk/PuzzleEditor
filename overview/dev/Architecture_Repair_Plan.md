## 1. 决策：分批实施，逐批验收

建议分六批实施，每批围绕一个可验证的目标交付。当前问题既包含保存与撤销的正确性缺陷，也包含类型保障、模块边界和组件职责问题；同时修改会放大影响范围，难以判断行为变化来自缺陷修复还是结构调整，也不利于回退。

保留现有领域模型、扁平数据结构、Context + Reducer 和领域切片。优先把状态与项目操作的约束集中起来，并用回归测试保护；再收紧类型和规范、整理组件；性能优化由测量结果决定。沿用现有 React/Vite/Electron 技术栈。

## 4. 第一批：统一状态约束与撤销语义

### 4.1 目标与修改范围

修复演出图级增删改不标脏、不进入历史、只读保护遗漏，以及保存后 Undo/Redo 标记错误。主要涉及 `store/types.ts`、`store/reducer.ts`、`store/slices/`、`store/context.tsx` 和对应测试。

### 4.2 技术设计

**集中定义操作策略。** 建议新增 `store/actionPolicy.ts`，通过 `Action['type']` 的穷尽映射描述每种 Action：操作类别、是否可能改变项目内容、历史策略、只读权限。新增 Action 缺少策略时应被类型检查发现；领域切片仍负责自身更新逻辑，避免再维护互相漂移的全局名单。

历史策略至少区分“记录快照”“保留历史”“形成历史边界”，项目内容变化与进入历史分别判定。类型分类说明允许的行为，实际是否产生新版本还要由数据是否真正改变决定。无效目标和已满足状态的操作不能空耗历史。

审核范围覆盖所有 Action，不仅补齐三个 Graph Action；尤其核对连线几何属性、排序、外部资源状态同步、初始化、时间戳同步和 Undo/Redo。只读检查必须在所有用户内容修改入口生效，包括最外层处理的 Undo/Redo；导航、选择、消息等浏览行为仍可使用。初始化和受控同步单独分类。

**保存版本与编辑版本分离。** 建议在会话状态中增加 `sessionId`、当前内容版本标识和已保存版本标识。历史项同时保存项目快照及该快照的版本标识；新的编辑分支分配新标识，不复用被撤销的标识。保留当前 50 条历史上限。

- 正常内容修改推进当前版本；Undo/Redo 恢复快照及其版本。
- 当前版本等于已保存版本时为 clean，否则为 dirty；现有 `ui.isDirty` 可以暂作兼容派生字段，由统一入口更新。
- 保存完成确认携带“会话 + 实际写入版本”，只确认对应版本；即使保存期间继续编辑，也不能清除新版本的 dirty。
- 初始化/成功切换项目同时重置会话、历史和保存基线。更新保存时间戳不产生一次用户编辑。
- 文件中附带的面板尺寸、导航、树展开等 UI 偏好随保存快照记录，但不混入业务撤销和业务未保存提醒；画布中属于项目数据的坐标与连线配置按内容修改处理。
- 回到已保存的历史快照应变为 clean；手工编辑出相同内容可以保守保留 dirty，本轮不要求引入全项目深比较或哈希计算。

保存逻辑在本批接入最小的版本确认协议，第二批再集中处理完整文件工作流，避免两批之间出现接口断层。

**保留不可撤销操作的语义。** `UX_Flow` §7.6 对 Apply Delete 明确要求二次确认且不可撤销，不能把所有写操作直接等同于可撤销。建议成功执行后形成历史边界，清理可能复活已永久删除资源的旧快照，并保持 dirty；在技术设计中写明历史清理的用户影响。软删除与复原使用普通可撤销编辑语义。

### 4.3 验收条件

- 演出图创建、改名、删除后显示未保存，Undo/Redo 得到正确项目内容。
- 编辑 → 保存 → Undo 为 dirty；Redo 回到保存快照为 clean；撤销后新建分支不会错误复用保存基线。
- 只读时增删改、拖拽修改、Undo/Redo 均不能改变项目；导航、选择和查看引用正常。
- 空操作不增加历史；超过 50 次操作后历史上限有效；永久删除不会通过旧历史复活。
- 校验、导航、消息、时间戳同步不产生无意义的用户编辑历史。

## 5. 第二批：统一保存与项目切换流程

### 5.1 目标与修改范围

所有项目替换入口都通过同一保存保护流程，保存错误和取消不会清除当前修改。主要涉及 `hooks/useProjectActions.ts`、`hooks/useAutoSave.ts`、`components/Layout/Header.tsx`、`ProjectMenu.tsx`、保存确认弹窗、快捷键和现有 Electron API 包装。

### 5.2 技术设计

**共享项目会话流程。** 建议提取会话操作服务/Hook，由一个共享实例管理当前操作，而不是每次调用 Hook 都创建独立保存锁。Header、ProjectMenu、快捷键、自动保存只发出请求；平台适配器负责文件选择、读取、写入，UI 负责弹窗和状态展示。

明确操作阶段：准备候选项目 → 检查当前修改 → 保存/放弃/取消 → 提交候选项目。读取和解析候选文件时保留当前项目；最终以一次会话提交同步项目数据、路径、UI、历史和保存基线。失败时完整保留当前会话，最近项目和上次路径仅在成功加载后更新。

新建、普通打开、最近项目打开、浏览器文件导入和启动恢复都复用该流程；启动恢复也要防止迟到的加载覆盖用户已经开始的操作。现有内部 Stage/Node/Graph 导航继续由导航切片管理，无需引入 URL 路由框架。

**显式表达异步结果。** 保存返回可区分的结果，例如 `saved`、`cancelled`、`failed`、`downloadInitiated`。`saved` 附带会话、版本和目标路径；UI 回调保留 Promise 语义，删除固定 100ms 定时继续的逻辑。

- Save and Continue 只有在实际保存成功且当前版本仍与保存版本一致时才提交候选项目。
- 保存失败或保存对话框取消时保留 dirty，显示 English 错误/状态信息并进入 Messages；提供重试和取消。
- 保存过程中出现新编辑，完成后仍保持 dirty，切换流程继续受保护，不能静默放弃新增内容。
- Discard 是对本次替换的明确选择，不提前执行全局 `MARK_CLEAN`；随后文件选择取消或解析失败时，原项目依然保持 dirty。
- 浏览器下载无法确认用户最终落盘。建议只显示下载已发起，并保守保留 dirty；需要切换时由用户使用既有 Discard 明确继续。可验证的文件写入接口才返回 `saved`。

**统一处理写入顺序。** 手动保存、自动保存、项目设置保存共享同一个协调入口；对同一文件串行写入。保存请求固定捕获当时的会话、路径、内容版本和快照，迟到结果不得更新新会话。连续请求可以合并为保存最新待保存版本，但不能让较旧内容最后覆盖新内容。自动保存调度读取最新状态，测试持续编辑时是否仍按设定周期运行。

保存项目设置时明确保存的是哪些完整内容，避免从磁盘回读旧项目再覆盖其他未保存修改。导出继续独立执行校验与运行时归一化，导出成功不代表完整项目已保存。

### 5.3 验收条件

- 每个打开/新建入口均覆盖 Save、Discard、Cancel，以及后续选择器取消和读取失败。
- 注入延迟、失败和取消结果，确认失败前后项目、路径、历史和 dirty 均正确。
- 保存 A 期间新增修改 B：文件对应 A，当前 B 仍 dirty；之后保存 B 成功才 clean。
- 自动保存与手动保存重叠时写入顺序确定；旧项目迟到的回调不改变新项目。
- 实际 Electron 临时项目完成创建 → 编辑 → 保存 → 重开；浏览器完成上传和下载交互检查，结果说明准确。
- 核对窗口关闭与应用退出当前行为，记录是否已接入保护。若需要新增主进程关闭协议，单独列为后续兼容任务；本批不能据菜单切换测试声称关闭保护已经完成。

实施结果见 [第二批记录](./Architecture_Repair_Batch2.md)。第二批当时未包含关闭生命周期兼容任务；该后续任务已于 2026-10-08 单独完成，见 [未保存项目关闭保护](./Window_Close_Protection.md)。原生窗口关闭/应用退出现已复用项目会话的保存确认，并补充真实 Electron 关闭验证。

## 6. 第三批：建立导入校验和兼容边界

### 6.1 目标与修改范围

防止任意 JSON 被归一化成空项目，同时保留编辑未完成项目和有证据的旧格式的能力。主要涉及 `utils/projectNormalizer.ts`、`types/project.ts`、项目加载入口和导入测试夹具。

### 6.2 技术设计

将流程拆为：JSON 解析为 `unknown` → 格式识别 → 最小结构校验 → 已知兼容迁移 → 归一化 → 业务校验 → 构建候选会话 → 提交。归一化只补齐允许缺省的字段，不承担格式识别。

建立有样例支撑的兼容清单：当前 `puzzle-project`、`puzzle-export`、确有结构依据的原始 ProjectData，以及能找到真实样例的旧格式。当前注释声称支持的历史格式不能仅凭名称判定支持；未知 `fileType` 不得落入原始项目兜底分支。

区分不可加载的结构错误和可在编辑器中修复的业务问题：

- 拒绝：无关对象、null/数组顶层、字段容器类型错误、缺失必要根结构、明确不支持的格式版本等。包含字段位置和原因，原会话不变。
- 允许加载并报告：结构有效，但缺少初始状态、引用目标尚不存在、存在待删除资源等工作中问题；继续沿用项目校验与导出阻断规则，避免把编辑过程中的项目一律拒之门外。
- 可兼容补齐：已有规范允许省略的集合、UI 偏好及旧字段默认值；记录迁移规则和警告，不静默丢弃无法识别的重要数据。

格式版本兼容依据文件格式字段和实际结构判断，不能把用户可编辑的 `meta.version` 简单当成唯一 Schema 版本。运行时导出导入后形成待另存的编辑项目，不把导出源路径自动设置为可直接覆盖的 `.puzzle.json` 保存目标。

### 6.3 验收条件

- 当前示例及已确认旧格式可加载，ID、引用、排序和参数语义保留。
- 无关 JSON、错误类型、损坏根结构和不支持的格式得到明确错误，不改变当前数据和路径。
- 可编辑的业务错误进入消息/校验结果，仍能导航修复；导出按既有错误级别阻断。
- 加载 → 保存 → 重开，业务数据与 UI 恢复语义一致；加载 → 导出与既有规范一致。

实施结果见 [第三批记录](./Architecture_Repair_Batch3.md)。已建立受校验的导入边界、真实历史兼容夹具、诊断修复导航和可重复的文件往返检查；累计 140 个回归与 Electron 11 项检查通过，另完成浏览器直接操作验收。原生关闭生命周期兼容任务仍独立待办。

## 7. 第四批：恢复类型保障与自动检查

### 7.1 执行顺序

1. 补齐与 React 19 对应的类型依赖，更新锁文件，重新统计诊断。审查中的 3540 条严格检查诊断包含大量连锁错误，不能作为实际修复量估算。
2. 明确 Context、Store Hook、Action、保存结果、导入结果和图节点接口的类型，验证错误 Action 及错误载荷会被检查发现。
3. 按领域收紧 `any`：外部 JSON 使用 `unknown` 与校验；变量值使用符合现有领域的联合类型；Inspector 使用明确的更新类型；移除伪造不完整 EditorState 的强制转换。
4. 逐步解决空值、索引和回调参数问题，最终开启根前端 `strict: true`。每个中间提交保持现有检查通过，剩余严格检查诊断按类别跟踪；禁止通过全局关闭检查、排除业务文件或批量 `@ts-ignore` 达标。
5. 建立 lint、格式与编码检查；固定配色/间距与动态画布坐标分别制定规则。纯格式整理单独提交，避免掩盖行为修改。

### 7.2 已建立的检查入口

## 8. 第五批：整理依赖边界与组件职责

第五批主体重构及已实现交互验收完成，原验收中的独立缩放仍未闭环，详见 [第五批记录](./Architecture_Repair_Batch5.md)。当批累计 180 个回归、严格检查、构建和 Electron 11 项通过；浏览器完成黑板、画布、条件、导出与重开的回归。以下保留分层和拆分要求作为维护约定，实际目录见 [架构指南](./Architecture_Guide.md)。

### 8.1 边界设计

| 职责 | 推荐依赖 | 改进重点 |
| --- | --- | --- |
| 领域类型与纯计算 | `types`、必要的纯工具 | 不要求完整 EditorState；校验结果等领域类型归位 |
| Store 与 Reducer | 领域类型、纯计算 | 统一状态约束，保持纯更新，文件 I/O 放在会话流程 |
| 项目会话与业务 Hook | Store、纯计算、平台适配接口 | 管理保存、加载、错误和顺序 |
| 平台适配器 | 平台 API、文件/结果类型 | 封装 Electron 与浏览器差异，不直接操纵 UI |
| 组件 | 业务 Hook、选择结果、通用 UI | 展示和发出意图，减少重复业务规则 |

已移除无人使用的 `api` 与旧 Electron Hook/barrel，IPC 包装迁入 `platform/electron.ts`，项目导出经 `ProjectSession` 和注入式平台接口；网络翻译迁入 `services/translation`。沿用第四批 ProjectData 接口原则，项目诊断契约移至 `types/validation.ts`，FSM/演出图校验不再接收整个 Store，引用/诊断导航移入 `store/navigation`。

### 8.2 拆分顺序

1. Blackboard：四个页签视图、筛选与引用统计、资源操作和拖拽排序分别明确职责，保留公共选择与导航约定。
2. PresentationCanvas：拆分可测试的交互组织、节点/边渲染和坐标计算，复用现有画布 Hook；随后评估 FSM Canvas 中相同逻辑的复用价值。
3. 条件编辑与其他大型 Inspector：只对职责混杂的部分拆分，保持事件和参数绑定行为。
4. 将固定颜色、间距、菜单和弹窗样式逐步归入现有主题体系；运行时坐标、变换等动态样式允许通过明确接口传入。

拆分目标是业务职责清楚、局部修改影响可控；文件行数用于发现问题，不作为唯一验收标准。每次只整理一个子系统，使用已有测试验证行为，并同步 `Architecture_Guide.md`、相关开发说明和样式规范。

## 9. 第六批：测量性能并完成验收

本批已实施，详见 [设计与验收记录](./Architecture_Repair_Batch6.md)。真实示例、中型和大型固定夹具完成生产模式前后对照；大型 Blackboard 挂载 p50 从 302.6 ms 降至 17.0 ms，内容编辑从 276.0 ms 降至 6.3 ms。优化范围是批量引用统计，未更换 Store 或画布实现。187 个回归、全量规范检查、生产构建、Electron 11 项和浏览器文件往返通过；测量边界及剩余功能见记录，不把缩放算作已测通过。以下保留本批测量原则。

先建立固定的真实示例和合成项目夹具，记录 Stage、PuzzleNode、状态/边、演出节点和引用的数量、测试设备及构建模式，再比较同一场景的结果。

测量黑板切换与筛选耗时、引用扫描次数、画布位置提交、加载/序列化/校验耗时及内存使用。原计划中的独立缩放尚未实现，留待功能补齐后测量；磁盘正确性另由真实 Electron 检查覆盖。记录多次运行的分布，区分首次调用和后续操作；不能把开发模式的重复渲染直接当作生产性能结论。

根据结果选择优化：若引用扫描占主要开销，建立共享引用索引并验证更新正确性；若全量 Context 通知产生主要渲染成本，再划分领域订阅或引入必要的选择机制。不要仅因存在大组件或 Context 就替换状态库。没有明显瓶颈时交付测量结论即可。

测量准备时先明确典型项目规模和可接受交互预算，再执行前后对照；用实际数据确定改进目标，不在未测量时承诺帧率或提升比例。任何优化都必须通过前五批的正确性检查。

最终执行浏览器完整交互回归、Electron 临时项目文件往返和构建检查；真实原生文件操作、模拟故障测试、静态检查和未验证项分别记录。
